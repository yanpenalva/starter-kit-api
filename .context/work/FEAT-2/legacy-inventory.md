# Legacy behavior inventory

**Source:** `starter-kit-laravue` commit `377cd6ee45edad68bfadeefc32fb3762fc4a3552`, inspected statically and read-only. Paths below refer to that exact source tree. No credential values or personal records are copied into this inventory.

| Area | Observed in the pinned source | Greenfield disposition |
| --- | --- | --- |
| Authentication | `routes/api/auth.php`, `app/Actions/Auth/LoginAction.php`, and `tests/Feature/Api/Auth/AuthenticationTest.php`: login uses the `web` guard and regenerates a session, then also issues a Sanctum personal access token. The response contains the token. `LogoutAction` invalidates the session and deletes every personal access token belonging to the user; its tests assert this behavior. | Use Sanctum stateful session cookies and CSRF for the first-party SPA. Do not issue a PAT from SPA login and do not revoke unrelated integrations on logout. Bearer tokens need a separately approved integration contract. |
| LDAP | LDAP-specific login, registration, and lookup services and routes exist in `resources/js/services/LdapLoginService.js`, `resources/js/composables/Authenticate/useLDAPAuthenticate.js`, and related UI files. | Excluded by the accepted ADR decision. Do not port routes, screens, connection settings, or LDAP-specific identity rules. |
| Public registration and verification | `routes/api/user.php`, `RegisterExternalUserRequest`, `CreateExternalUserAction`, and `VerifyAction`: registration requires CPF, accepts only a fixed guest-role enum, queues a verification email, and starts without active access. Verification updates `email_verified_at`; a later administrative activation is described in legacy text. | CPF is optional in the new API. Email verification automatically activates only the basic profile; it does not grant administrative privileges. The accepted decision supersedes stale administrative-approval wording in Issue #14. Never accept role, activation, or verification fields from public input. |
| Verification links | `app/Mail/SendVerifyEmail.php` builds a temporary signed API URL and then changes its path with `str_replace`. | Do not rewrite a signed URL after signing. Issue #14 owns an explicit frontend base URL and a callback that verifies signature, hash, expiry, and state. The actual frontend/API domains remain `NOT FOUND`. |
| Password flows | `ForgotPasswordAction` uses Laravel's password broker and queues mail; it returns a client-visible failure when the broker reports failure. `ResetPasswordAction` changes the password. The routes apply throttling to the request path. | Build the flow under Issue #15 with generic non-enumerating responses, one-use/expiring tokens, explicit throttles, and SPA URLs. Legacy messages and their enumeration behavior are not requirements. |
| Users and CPF | User migration/model include CPF. The model strips non-digits, while public and administrative request rules require CPF. `CreateUserRequest` and `UpdateUserRequest` also accept activation and role fields for privileged operations. `UserResource` delegates to model serialization. | Use the approved optional CPF rule: normalize to 11 digits, validate check digits, unique when supplied, and restrict reads to the subject or a specific permission. Define explicit Resources and permitted input per endpoint; never expose another user's CPF or rely on model serialization as the API contract. |
| Roles and permissions | Spatie Permission is used. Enums define `administrator`/`guest` and permission keys under users, roles, and activity logs. Policies check permissions for several operations; route middleware also uses `auth:sanctum`. | Package direction is accepted, but the business role/permission matrix and names remain `NOT FOUND` until Issue #16. Do not reuse the legacy catalog or assume that an administrator label alone authorizes CPF access. |
| User search and pagination | `ListUserAction` searches ID/name/email/role, maps a small column allowlist for sorting, and returns all rows unless `paginated` is true; page size is supplied as `limit`. The SPA's Quasar table owns rows-per-page choices. | Keep API pagination independent of Quasar. Use only documented `page`/`per_page` parameters, bounded page size, an explicit response Resource, and per-endpoint allowlisted filters/sorts. Never pass arbitrary client column names into SQL. |
| Audit | `LogsActivity` writes model attributes/diffs and removes `password`, `password_confirmation`, `remember_token`, `token`, and `access_token` from selected diffs. CPF is not in this exclusion list. Create/delete capture model serialization. `CleanActivityLogCommand` and its feature test delete **all** activity rows, not rows older than a retention cutoff. | Follow ADR 0005: Activitylog v5, explicit events and permitted diffs, CPF and credentials excluded, permission-gated read access, and 90-day event retention. Define backup retention before production collection. Do not reuse the denylist or the destructive cleanup command. |
| Admin bootstrap and examples | `database/seeders/UserSeeder.php` seeds and assigns an administrator from `starterkit.admin.*` configuration. The tracked legacy `.env.example` includes fixed development/example database and administrator settings. Their values are intentionally omitted here and are not evidence of production use. | No fixed production credentials, automatic first-user elevation, or production admin seeder. The accepted design promotes an explicitly selected verified account through a restricted operational command, transactionally and idempotently. Rotate any example value if it was reused in a real environment; whether it was used is `NOT FOUND`. |
| SPA auth state | `resources/js/services/AxiosClient.js` sends credentials and XSRF data. `useAuthStore.js` persists user, role, and permission state in local storage and treats a cached user object as logged-in state. The legacy login result also contains a PAT, while the store's persistence does not make it the authoritative session. | The browser's cached user/permission state is presentation data only. The API session and server-side authorization remain authoritative; reload the profile from the API and clear client state on 401/419. Do not store credentials or use local storage as the authentication mechanism. |

## Static-inspection limits

- Source and tests show intended code paths; they do not prove production configuration, deployed routes, live credentials, or runtime behavior.
- Exact domains, runtime secrets, production seeder usage, deployment state, and behavior of uninspected integrations are `NOT FOUND`.
- No attempt was made to validate or use any credential-like value from the legacy example configuration.

## Cross-cutting classification

- **Implemented behavior:** the table records the observed route, action, data, email, authorization, audit, or SPA paths and distinguishes code behavior from production behavior.
- **Dead or unrouted behavior:** no orphaned workflow was established by this bounded inspection (`NOT FOUND`). LDAP does have referenced routes and UI/service files, but it is excluded by product decision rather than classified as dead.
- **Domain-specific behavior:** LDAP; the `administrator`/`guest` role catalog and its permissions; CPF-required registration; and legacy activation messages. These do not transfer automatically.
- **Technical risks to prevent:** SPA session plus PAT in one login, global PAT revocation on logout, fixed example credentials, localStorage treated as authenticated state, Quasar-specific pagination, post-signature URL mutation, CPF/secret capture in audit, and cleanup that deletes every activity row.
- **Open decisions:** exact production SPA/API domains, session/CORS settings, mail delivery and callback paths, final permission names, and production use of legacy example values remain `NOT FOUND` or belong to API #14–#16 and deployment planning.
- **New greenfield outcomes:** limited pre-verification session; automatic activation after email verification; optional validated/unique CPF with access restrictions; explicit admin bootstrap; allowlisted 90-day audit; framework-neutral pagination and HTTP contracts. These are requirements from the accepted ADRs and owning issues, not copied legacy behavior.
